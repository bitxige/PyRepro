# Shared Review Policy

请审查项目 `{PROJECT_NAME}` 中 `{TARGET_SCOPE}` 范围内的代码，但不要进行
任何代码修改、生成补丁或执行重构。

审查目标是评估当前代码质量，并说明质量水平、主要问题和改进优先级。只检查
`TARGET_SCOPE`，以及理解其职责和交互所必需的最小周边上下文。

请重点检查以下方面。

## 1. 功能实现复杂度与冗余

- 当前功能实现是否存在不必要的复杂设计。
- 是否有重复逻辑、过度抽象、无效封装或可以简化的流程。
- 是否存在为了实现简单功能而引入过多层级、过多中间变量或过多辅助函数的
  情况。
- 是否存在因不必要复杂性而降低可读性或可维护性的实现流程。

## 2. 命名与代码组织

- 所有函数命名是否合理、清晰，并符合 Python 项目的常见规范。
- 变量名是否准确表达含义；是否存在过短、过泛、误导性或与上下文不一致的
  命名。
- 当前文件在 `{PROJECT_NAME}` 中的目录位置是否合理，功能划分是否清晰。
- 是否有类、函数或模块更适合放在其他目录或文件中。
- 是否存在模块职责不清、文件边界模糊或功能耦合过强的问题。

## 3. Public classes 的 docstring

- 所有 public classes 是否都提供了 docstring。
- docstring 是否与项目中既有代码风格保持一致。
- docstring 是否在确有必要时使用 Google 风格的 Args、Attributes、Returns、
  Raises 等部分。
- docstring 是否准确描述类的职责、参数、属性和行为，而不是过于笼统或与实现
  不一致。

## 4. Pytest 中 assert 使用的合理性

- 检查与 `{TARGET_SCOPE}` 对应的 pytest 测试文件中 assert 的使用。
- 判断 assert 是否覆盖关键行为，还是存在过度断言、重复断言或与实现细节绑定
  过强的问题。
- 是否有 assert 使测试变得脆弱、难维护，或偏离测试的核心意图。
- 是否存在可使测试结构更清晰的方式，例如参数化、拆分测试用例或减少重复
  setup。

## 输出要求

请输出一份评估报告，包含：

- 总体质量水平（优秀、良好、一般或较差）及理由；
- 主要优点；
- 按高、中、低优先级排序的问题列表；
- 每项问题的具体文件、类、函数或测试位置；
- pytest assert 使用的单独评估；
- public classes docstring 完整性与风格一致性的单独评估；以及
- 最终合入建议，包括是否建议先清理或补充文档、测试。

## 结论约束

- 不需要直接修改代码、生成 patch 或重构实现。
- 结论必须基于具体代码证据。
- 单独一个静态信号不能机械地产生 finding。
- 不要输出 scratch work、计划过程或自我推理。
